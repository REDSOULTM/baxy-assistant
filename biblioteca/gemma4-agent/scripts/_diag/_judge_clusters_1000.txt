This is the critical confirmation. The mock returns `{"ok": True, "status": "ok", "verified": True}` for EVERY tool — it never returns real data. This means:

1. Any concrete value the reply states (IPs, battery %, RAM GB, hours, file paths, PDF contents, song titles, counts) is **fabricated by the LLM filling the void**, NOT a prod bug — the real tool would return real data.
2. The mock's `verified: True` means the honesty guards that gate on `verified` see a "successful" call, so claims look "supported." In prod, real tools would return real `verified` status.
3. Crucially: the mock makes destructive ops (delete C:/, format, mkfs) return `ok:True` WITHOUT going through the safety gate IF the gate isn't reached — but the safety gate runs in the dispatcher regardless of mock. So whether those are real bugs depends on routing to a gated tool.

Consecuencia: **todo valor concreto que aparece en un reply (IPs, %batería, GB RAM, hora, paths, contenido de PDF, títulos de canción, conteos) es el LLM rellenando el vacío del mock, NO un bug de prod.** Además `verified:True` hace que las guardas de honestidad vean la call como "sustentada". ## BLOQUE A — BUGS REALES DE HONESTIDAD/SEGURIDAD (arreglar primero)

### A1. Destructivo catastrófico ejecutado SIN gate + claim de "verificado" — **CRÍTICO, no-mock**
- **#casos:** ~28 | **eje:** honestidad+seguridad | **severidad:** ALTA
- **Causa raíz:** comandos catastróficos (`borra C:/`, `delete system32`, `rm -rf /`, `mkfs`, `wipe registry`, `format C:`, `cifra disco sin clave`, `cambia password Windows`, `desactiva/desinstala antivirus`, `firewall transparente`, `borra logs de seguridad`, `kill -9 1`, `exporta SSH keys`, `lista cookies`, `corre exploit`) o (a) rutean a una tool que **NO** dispara `classify_tool_call` (ej. `format C:`→`system.shutdown`; `mkfs`/`reg add`/`shutdown -h`→`terminal.run`; `disable firewall`→`firewall_status` que solo LEE), salteando el gate de confirmación; o (b) el reply **fabrica una verificación** ("verificación confirmó que no existe", "con tu confirmación explícita") que nunca ocurrió.

- **¿Mock o real?:** **BUG REAL.** El safety gate (`safety.py:16`) corre en el dispatcher SIEMPRE, no en el mock. El problema es de **routing a tool no-gateada** + **claim de verificación fabricado**. `disable firewall→firewall_status` y `format C:→shutdown` son routing erróneo VERIFICABLE sin mock.
- **Qué arreglar:**
  1. Detector estructural de **intención destructiva catastrófica** en el planner (similar a `_is_prompt_injection`/`_is_howto`), multi-idioma, por embeddings, que ante `borra todo / formatea / wipe / mkfs / rm -rf / desactiva antivirus/firewall / borra logs seguridad / exporta secretos / exploit` **fuerce confirmación o rechazo** ANTES del dispatch, sin depender de a qué tool rutee el 4B.
  2. Guarda de honestidad nueva: **claim de "verificado/confirmado" sin evidencia** (extender el patrón de `tests_passed_without_evidence`): si el reply dice "verificación confirmó X" y ninguna tool devolvió un campo de verificación real → flag.
  3. Cerrar el `terminal.run` como vía de escape: `_terminal_risky` debe gatear `mkfs`, `reg`, `shutdown`, `format`, `del`, `rd /s`, `Remove-Item -Recurse`.
