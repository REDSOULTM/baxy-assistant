# Reducing Prefill Latency for a Local Gemma 4 (E2B Q4_K_M) Voice Assistant on llama.cpp b9384, Flash-Attention OFF

## TL;DR
- **Your single biggest, safest win is to STOP dropping the tool schemas in pass-2.** With prefix caching working (it already is — your "minimize the window" turn prefilled only 1,656 tokens), keeping the system+tools prefix byte-identical turns pass-2's 5,363-token / ~1,083 ms re-prefill into a ~50–100 token / <100 ms cache hit, saving roughly 1 second per action turn at zero risk. The "summary slimming" 1.5k-token saving is a net loss because it busts the cache.
- **Re-enabling `--cache-reuse N` is the WRONG lever and is unnecessary.** Gemma 4's shared-KV architecture makes the server explicitly refuse `--cache-reuse` ("cache reuse is not supported - ignoring n_cache_reuse = 256", issue #21468). What you actually need is ordinary prefix caching (on by default), which was fixed for `--swa-full` SWA models by PR #21749 (closes #21468) and is present in your b9384 build. Keep `--swa-full`; do not add `--cache-reuse`.
- **The crash (#22527) is tied to the Flash-Attention path interacting with the SWA KV checkpoint; with FA OFF on the small E2B model it does not reproduce (your 37/37).** KV-cache quantization (`-ctk/-ctv q8_0`) is off the table because it requires FA; with FA off Gemma 4 already pads the V cache to head-size 512, so quantization both fails to engage the fast path and risks OOM. Focus on prefix stability, not kernel tricks.

## Key Findings

1. **Root cause of crash #22527 (FA + SWA, Gemma 4).** The issue "Gemma 4 31B: illegal memory access after SWA KV cache checkpoint with Flash Attention enabled" was opened Apr 29 2026 by Xuan-GUo on build b8975-59237bfbb (NVIDIA RTX 4060 Ti 16 GB, model gemma-4-31B-it-heretic.i1-IQ3_XXS.gguf). It reports a CUDA "illegal memory access" surfacing at `ggml-cuda.cu:3083` in `ggml_backend_cuda_synchronize` → `cudaStreamSynchronize`, **immediately after the second SWA KV cache context checkpoint is created** with `--flash-attn on`. Because `cudaStreamSynchronize` is only where an *asynchronous* CUDA error surfaces, this is not necessarily the origin. The circumstantial evidence ties the fault to the **SWA checkpoint/state path combined with the FA kernel on Gemma 4's mixed head sizes (512 full / 256 SWA)**. The issue has zero maintainer comments and no linked PR, so no authoritative root-cause confirmation exists. Critically, the reporter found that `--flash-attn off` does **not** cleanly cure it on the 31B model — verbatim: "Disabling Flash Attention (--flash-attn off) → server fails to allocate VRAM due to V cache padding for mismatched layer sizes." It converts the crash into an OOM.

2. **Why FA-off works for you but not the 31B reporter.** With FA off, the FA CUDA kernel is removed from the compute graph entirely, so the FA+checkpoint interaction that crashes cannot occur. The 31B reporter then hit OOM because Gemma 4 pads the V cache to the maximum head size (512) across all layers when FA is off — documented intentional behavior in `src/llama-kv-cache.cpp` ("the V embeddings have different sizes across layers and FA is not enabled - padding V cache"). On the small **E2B** model at 16,384 context this padded cache still fits your 4 GB ceiling, which is why you measure 37/37 turns OK with FA off vs 6/37 with FA on. **Conclusion: FA-off is the correct, stable choice, and it makes the checkpoint/cache path safe on E2B because the crashing FA kernel is no longer present.** This is a hypothesis-grade inference (no maintainer confirmation), so validate with a 50-turn soak.

3. **`--cache-reuse N` vs prefix caching — these are different mechanisms.**
   - **Prefix caching** (`cache_prompt: true`, default ON) reuses the longest common *prefix* between the new prompt and the slot's cached tokens. This is exactly what your two-pass turn needs. It was broken for SWA models (server forced full reprocessing) until **PR #21749 "server: ensure prompt caching for SWA models"** (author "shipped-it"), which verbatim "Setting pos_min_thold = 0 when swa_full is enabled (any cached position is useful)" and "Skipping checkpoint restoration logic when swa_full is enabled (unnecessary since cache is full-size)." That PR **closes #21468** and is in your build. Your observed 1,656-token pass-1 prefill proves it is already working.
   - **`--cache-reuse N`** (a.k.a. KV-shifting / hole-filling) is the mechanism that Gemma 4 explicitly refuses. Issue #21468, opened by user "phuryn" on Apr 5 2026 (build b8660, RTX 2000 Ada, gemma-4-E2B/E4B-it-GGUF), logs verbatim "cache reuse is not supported - ignoring n_cache_reuse = 256" with "sim = 0.000," causing a "~46K tokens, ~96 seconds" full re-eval — because of Gemma 4's shared-KV layers. It is also "almost definitely not what you want" (maintainer discussion #22354) because it keeps stale tokens around. **Do not enable it.**

4. **Optimal prefix-cache config for Gemma 4 + SWA + FA-off in b9384:**
   - Keep `--flash-attn off` (mandatory for stability).
   - Keep `--swa-full` — this is what makes prefix reuse work for a 5k+ prompt: it allocates a full-size SWA cache so tokens outside the sliding window are NOT pruned, so any cached prefix position is valid; it also disables the buggy checkpoint-restore path per #21749.
   - Leave `cache_prompt` at its default (true). Do **not** set `--cache-reuse`.
   - Set `--ctx-checkpoints` low (e.g., 1–2) or rely on swa-full making them unnecessary — Gemma 4 checkpoints cause severe RAM bloat (see Details).
   - Keep `-c 16384` and a single slot (`-np 1`) for the per-profile child server.
   - **Dangerous defaults to avoid:** KV quantization with FA off; high `--ctx-checkpoints` (RAM bloat); and `--cache-reuse` (unsupported on Gemma 4).

5. **Prefix-stability checklist (keep byte-identical to maximize cache hits):** the tool set (your pass-2 bug), timestamps/dates injected into the system prompt, message reordering, varying `tool_call` IDs, non-deterministic JSON key ordering in tool schemas, varying `chat_template_kwargs` (e.g., toggling `enable_thinking`), whitespace/punctuation edits, and BOS handling. Everything *before* the first point of divergence must be identical token-for-token. This is corroborated by arXiv:2601.06007, "Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks" (Elias Lumer et al., PricewaterhouseCoopers, 2026), which quantifies that prompt caching "reduces API costs by 41–80% and improves time to first token by 13–31% across providers," and warns that "naive full-context caching … can paradoxically increase latency" — i.e., prefix stability, not raw cache size, is what matters (evaluated across OpenAI, Anthropic, Google on DeepResearch Bench, 500+ sessions, 10,000-token system prompts).

6. **The pass-2 trade-off, quantified.** Dropping tools saves ~1.5k prompt tokens but changes the prefix, causing a near-full re-prefill of 5,363 tokens (~1,083 ms). Keeping tools yields a cache hit so only the new tool-result tokens (~50–100) are prefilled (<100 ms). **Keeping the tools is decisively faster** — it converts pass-2 from ~1.28 s wall to roughly ~0.4 s (decode-dominated), cutting total action-turn LLM time from ~3.3 s toward ~2.0–2.3 s, comfortably under your ≤5 s target with headroom.

7. **Other prefill levers (ranked):**
   - **KV cache quantization (`-ctk/-ctv q8_0`): DO NOT USE with FA off.** It requires Flash Attention; without FA, llama.cpp dequantizes for every attention op (slower than no quant) and Gemma 4's FA-off V-cache padding risks OOM. (Apple-silicon and AMD/HIP guidance both confirm KV quant needs `-fa`; the fused fast path also requires symmetric K/V types.)
   - **`-b` / `-ub` tuning:** Prefill is compute-bound; on a 4 GB card a larger `-ub` raises the compute buffer and risks OOM, while a smaller `-ub` can sometimes improve cache locality (community reports show `-ub` sweet spots tied to GPU cache size). Your prefill is already fast (5,854 tokens / 1,222 ms ≈ 4,790 tok/s), so this is a marginal lever. Test `-ub 256/512` and measure VRAM on the real 4 GB target; revert if VRAM is tight.
   - **`--no-context-shift`:** prevents context-shift logic from running on long sequences; it doesn't speed prefill directly but avoids unexpected cache invalidation. Low-risk to add.
   - **The dominant lever remains prefix stability (Finding 6).**

8. **`tool_choice="required"` + synthetic `respond_in_natural_language` tool.** This forces every turn down a uniform tool-call path, eliminating the prose branch. It does **not** change the prompt prefix, so its prefill/cache impact is essentially nil — the prefill cost is the system+tools prefix, which is unchanged. Its only real benefit is output-path determinism, and `tool_choice="required"` support under Gemma 4 + `--jinja` is not guaranteed to be clean (hypothesis-grade). Low priority for latency.

9. **Confirming the ruled-out items.** Prefilling the `<|tool_call|>` token is (a) not cleanly supported under `--jinja` + tools, and (b) additionally blocked because assistant-prefill is rejected when thinking is enabled ("Assistant response prefill is incompatible with enable_thinking", issues #21889/#20861) — and your thinking is load-bearing. The ceiling of the win is the small decode (~0.4–0.9 s) vs the prefill, so it is not worth it — **confirmed, not refuted.** Streaming the confirmation to TTS is also confirmed ~0 win because the cost is prefill, not decode.

## Details

**Builds and dates.** Your b9090 → b9384 upgrade matters: PR #21749 (prompt caching for SWA models) had to be merged before your build for `--swa-full` prefix reuse to work; your live 1,656-token pass-1 prefill confirms it is active. Issue #21468 (Apr 5 2026, build b8660) is the canonical Gemma 4 "cache reuse is not supported" report and is closed by #21749. Issue #22527 (Apr 29 2026, build b8975) is the FA+SWA crash and remains open with no fix PR as of late May 2026.

**The shared-KV wrinkle.** Gemma 4's last `num_kv_shared_layers` reuse K/V tensors from the last non-shared layer (HF "shared KV cache" design). This is what trips `--cache-reuse` (KV shifting), and it is the architectural reason llama.cpp prints "cache reuse is not supported." It does **not** block ordinary prefix caching with `--swa-full`, which is the path you want.

**Checkpoint RAM bloat is real and Gemma-4-specific.** Issue #21690 (build b8724, RTX 3090 + 64 GB RAM) reports that with `-fa on -ngl 255 -c 16384`, "the entirety of the RAM space can be reached in 4 to 5 full prompt processing of about 16K tokens each," with the workaround "Setting `--ctx-checkpoints` to 1 or 0 with `-np 1` will prevent the server from going out of RAM." Discussion #21689 quantifies the worst case: "The default size of 'checkpoint' is 3600.054 MiB, more or less 4G … default checkpoint of Gemma-4-31B-it is '32' … 3600.054 MiB*32 = 115,201.73 MiB." Discussion #21480 measured Gemma 4 checkpoints at "531.309 MiB" vs 62.813 MiB for another architecture — "nearly 9x the RAM." On E2B the per-checkpoint size is much smaller, but the principle stands: cap checkpoints, and `--swa-full` makes them largely unnecessary.

**VRAM reality on 4 GB.** With FA off, the V cache is padded to head-size 512 on every layer. On E2B at 16,384 context this fits 4 GB; the lazily-loaded vision mmproj must stay lazy — loading it eagerly has crashed on CUDA (SIGABRT in `clip_model_loader::load_tensors`, issue #21402). KV quantization to reclaim VRAM is unavailable (needs FA). Therefore your VRAM budget is essentially fixed; do not spend it on a larger `-ub` or extra checkpoints. (Exact E2B KV numbers at 16,384/FA-off were not found in public logs; nearby E4B figures at 131,072 ctx FA-on were non-SWA 2,048 MiB / SWA 100 MiB — validate E2B empirically.)

## Recommendations (staged, by impact × safety)

**Stage 1 — Free, high-impact, zero crash risk (do first):**
1. **Stop dropping the tools in pass-2.** Send the identical system+tools prefix in both passes. Expected: pass-2 prefill drops from ~1,083 ms to <100 ms; total action-turn LLM time falls from ~3.3 s toward ~2.0–2.3 s. *Benchmark to watch:* server `timings.cache_n` / `prompt_n` — pass-2 `prompt_n` should be ~50–100, not ~5,300.
2. **Audit the prefix for per-request variation** (timestamps, tool_call IDs, JSON key ordering, `chat_template_kwargs`). Make everything before the divergence point byte-stable. *Benchmark:* cross-turn pass-1 prefill should routinely look like your 1,656-token case, not 5,854.

**Stage 2 — Confirm config, low risk:**
3. Keep `--flash-attn off` and `--swa-full`; confirm `cache_prompt` default true; ensure `--cache-reuse` is NOT set. Set `--ctx-checkpoints 1` (or accept swa-full making them moot) to cap RAM, with `-np 1`.
4. Run a **50-turn varied soak** to confirm zero CUDA crashes with the above. *Threshold that would change the plan:* any crash → capture the `create_check` log lines and `ggml-cuda.cu` assertion; if a checkpoint-path crash appears even with FA off, drop `--ctx-checkpoints` to 0 and re-test.

**Stage 3 — Marginal tuning, measure on the real 4 GB card:**
5. Sweep `-ub 256/512` (and `-b`) on the RTX 1650-class target, watching VRAM. Keep only if prefill improves without OOM. Add `--no-context-shift`.
6. Optionally add `tool_choice="required"` + a synthetic `respond_in_natural_language` tool only if you need output-path determinism — expect ~0 prefill benefit, and verify it doesn't break under `--jinja` + thinking.

**Do NOT do:** enable Flash Attention; enable KV quantization with FA off; enable `--cache-reuse N`; eagerly load the vision mmproj; prefill the `<|tool_call|>` token.
