## 1. Resumen ejecutivo brutalmente honesto

Carter v2 NO está roto, pero está **sobreingenierizado** y eso es exactamente lo que impide que sea un Jarvis local viable en modo texto. La causa raíz del A11 ("Quien eres → system_get_time") y de la latencia 30–60 s no es el modelo: es la **arquitectura del turno**, que arrastra una **burbuja experimental** (universal runner, intent_resolution, recovery classifier, perception monitor, verification manager, memory promoción automática, vision_router auto-probe) **encima** de un agent loop ya bastante complejo (3097 líneas en un solo archivo).

### Lo que está bien y se debe conservar

- **`brain_router.py` (141 líneas)**: Minimalista, sin clasificadores de idioma, ya está casi como debería estar. KEEP.
- **`ledger.py` (151 líneas)**: Honestidad reactiva (no inventa éxito si no hay evidencia). KEEP.
- **Backend `LlamaCppBackend`**: in-process, GPU offloading correcto, `flash_attn=True`, sampling sano (temp 0.0 tools / 0.6 reasoning, top_k=20, top_p=0.95). KEEP.
- **`probe_text_hardening.py`** estructurado por categorías A–I — buena base para extender.
- **`config.py`**: settings centralizados via env + .env + defaults, sin scatter de `os.getenv`.
- **Modelo**: `qwen3-8b-q4km.gguf` Q4_K_M es la elección correcta para tool calling (mejor que 14B Q2_K).
- **Política de seguridad** (`session/policy.py`, `_approval_prompt`): el aprobador high/critical existe y funciona.

### Diagnóstico de cabeza fría

- Es problema **del modelo**: parcial. Qwen3-8B Q4_K_M es bueno pero no perfecto en tool-calling, especialmente con un catálogo de 242 tools. La cuantización afecta obediencia marginalmente.
- Es problema **de arquitectura**: SÍ — principal. Demasiadas capas pidiendo decisiones al LLM, demasiados retries forzados, demasiado contexto inyectado.
- Es problema **de prompt**: SÍ — el system prompt tapa bugs en lugar de resolverlos arquitectónicamente.
- Es problema **de memoria**: SÍ — MEMORY.md ya está visiblemente contaminada.
- Es problema **de tests**: SÍ — los tests actuales no atrapan el A11; "100%" en probe_text_baseline no significa "Carter funciona".
- Es problema **de quant/config**: NO. Q4_K_M y los samplers están bien.

## 2. Mapa completo del sistema

### 2.1 Flujo de un turno de texto simple ("Quien eres")

```
CLI input ("Quien eres")
  └─► main.run() → engine.turn(req, session, on_token)
        ├─► resolve_reference() — anaphora resolver (no afecta este caso)
        ├─► _route():
        │     ├─► BrainRouter.decide(req)        # 35-50ms
        │     │     └─► _is_pure_conversational("Quien eres") → True
        │     │           (¡FALLA en este caso!  "Quien eres" NO está en _GREETING_TOKENS)
        │     │           → returns hint="agent_full"  (NO "agent_no_tools")
        │     ├─► _run_agent(req, hint_no_tools=False)
        │     │     ├─► self.system_context()    # probe.snapshot() ⚠ 500-1500ms WMI
        │     │     ├─► ContextWindowManager.build_context()
        │     │     └─► AgentEngine.run(user_text, hint_no_tools=False, ...)
        │     │           ├─► auto-detecta pure_conversational → True (segunda chequeo)
        │     │           ├─► _try_universal_plan_runner() → not_forced (se salta)
        │     │           ├─► _build_system_prompt(...) ⚠ ~7000 chars + memory + alerts + deps + vision_status
        │     │           ├─► _format_universal_skill_context(query) ⚠ skill embedding search
        │     │           ├─► first pass:  llm.chat_with_tools(messages, tools=[], think=True)  # ⚠ thinking ON
        │     │           │     └─► response.text="Soy Carter..." (sin tool_calls)
        │     │           ├─► _looks_like_personal_memory_query("Quien eres")
        │     │           │     └─► matches "favorito"/"sabes de mí"... NO matches "Quien eres"
        │     │           ├─► _should_accept_text_only_first_pass(...) → True
        │     │           ├─► stream_reply() o response.text
        │     │           └─► _guard_final_reply → _sanitize_reply → ledger guard
        │     └─► return TurnResult
        └─► output stream + memory.save_turn() + auto-promote cada 5 turnos
```

**Pregunta clave:** ¿Qué causa que `system_get_time` se llame para "Quien eres"?
**Respuesta:** Cuando el modelo en first-pass devuelve `tool_calls=[system_get_time]` directamente (decisión del LLM influida por el prompt gigante que menciona `system_get_time` 6 veces). El loop no lo previene porque NO hay un invariant que cubra el caso "identity → no system tools".

### 2.2 Flujo de acción con tools

Igual que el anterior, pero `chat_with_tools(messages, tools=[full_tools], require_tool=False)`. Tras tool_calls, normaliza, aplica `invariants.apply_all`, ejecuta con `_execute_tool_with_timeout`, registra en `ledger`, verifica con `VerificationManager`, monitor de percepción `PerceptionMonitor.snapshot()` antes/después, y vuelve al loop hasta `_direct_action_reply` o final answer.

### 2.3 Flujo de memoria

```
turn fin → memory.save_turn(user_text, reply)
        → memory.save_facts(result.facts)
cada 5 turnos → proactive.trigger_session_promote()
        → promote_recent(query, limit)
              ├─► rank_promotion_candidates() — sin exclusiones
              ├─► _is_promotable_candidate() — solo filtra ≥20 chars y JSON
              └─► remember(text, source) → MEMORY.md.open("a", ...)  ⚠ sin file lock
heartbeat (background) → consolidate_light/deep/rem → también escribe MEMORY.md
LLM consulta → memory.long_term_context(max=2000) inyectado al system prompt
```

### 4.2 ¿Por qué "Quien eres" tarda 30–60 s? Top 5 causas

1. **`probe.snapshot()` con WMI lento** (10–30 s en sistema con muchas apps/usuarios). Confirmado: `engine.py:59` es síncrono dentro del path crítico.
2. **First-pass LLM con `think=True`** (3–10 s). Carter activa thinking para conversación pura.
3. **Forced retry LLM call** si `_looks_like_personal_memory_query` o `_looks_like_resource_action_request` matchean por accidente (5–10 s extra).
4. **`active_app_reconsidered` retry** si hay app activa (5–10 s extra).
5. **System prompt rebuild + memory.relevant_facts + skill context** sin cache (300–800 ms).

**Suma típica:** 15–40 s explicados directamente. Los otros ~20 s de latencia restante salen del modelo en thinking + WMI lento.

## 11. Criterios de éxito — "Carter texto al 100%"

Carter texto se considera listo cuando:

- [ ] **Latencia conversación simple <5–8 s** verificada via `turn_trace.timing.total` en probe.
- [ ] **No tool calls accidentales**: probe completa A11 (Quien eres en ES/EN/PT/FR/DE) — 0 system_get_time, 0 memory_recall.
- [ ] **No basura en memoria**: tras 100 turnos de probe + dos heartbeats, `MEMORY.md` no contiene "Batman", "probe", "test", duplicados de color, ni `name:` con source≠user_stated.
- [ ] **Honestidad**: `result.errors` se reportan al usuario; ledger guard funciona; `gui_do` con `verified_outcome != confirmed` produce respuesta honesta.
- [ ] **Multipaso**: "abre Notepad y luego ciérralo" ejecuta dos pasos en orden.
- [ ] **Multilenguaje sin hardcodes**: ES, EN, PT, FR responden con tool routing correcto sin que ninguna lista ES/EN nueva sea necesaria.
- [ ] **Tests/probes**: probe_all 100%, probe_text_hardening ≥95%, A11 hardening 100%.
- [ ] **Trace por turno**: `last_turn_trace["timing"]` siempre presente.
- [ ] **Mantenibilidad**: `turn/agent.py` ≤ 800 LOC tras split.
- [ ] **Sin voz/cámara**: arquitectura preparada (interfaces aceptan modalidades) pero NO implementadas.

## Cierre

Carter v2 tiene un **núcleo sólido** y muchos buenos componentes (ledger, brain_router, llama_backend, sampling, intent_resolution, recovery), pero está sufriendo el clásico **"crecer hacia los lados"** en lugar de profundizar:

- Cinco subsistemas pidiendo decisiones al LLM antes de que el LLM responda.
- Tres mecanismos de retry que se activan unos a otros.
- Un system prompt enorme que intenta tapar bugs de arquitectura.
- Tests que cubren prompts pero no comportamiento.
- Memoria que ya está visiblemente contaminada.

La buena noticia es que **NO requiere reescritura grande**. Es desbroce + diet + un par de invariants nuevos + cleanup de memoria + instrumentación. Con el plan O1–O13 bien ejecutado en 2–3 sesiones, Carter texto cumple el criterio de éxito y queda en posición ideal para enchufarle voz y visión sin rehacer nada.
