5|1.1 Function calling confiable
6|Capacidad de emitir llamadas a herramientas estructuradas (formato libre: JSON, XML, Markdown, custom tags — lo que el modelo haga mejor)
7|Multi-tool en un solo turno: "abre Notepad y escribí hola" → debe emitir 2+ tool calls antes de devolver control
8|Tool result feedback loop: aceptar resultados de tools como input y continuar la cadena hasta resolver la misión
9|Argument fidelity: si el usuario dice "volumen a 50", el modelo debe pasar volume=50, no volume=0.5 ni volume="medio"
10|1.2 Honestidad por construcción (Valor 3)
11|El modelo debe poder seguir reglas prohibitivas estrictas del system prompt:
13|NO afirmar estado externo sin haber llamado read tool primero ("X está abierto" requiere list_windows() previo)
14|NO emitir replies genéricos ("(acción ejecutada)", eco del prompt)
15|NO inventar identificadores que no existen (URIs, paths, app names que el sistema no tiene)
16|Aceptar y producir estados explícitos: COMPLETED, PARTIAL, UNVERIFIED, NEEDS_USER, BLOCKED_BY_POLICY
17|1.3 Negation following (Valor 20)
18|Respetar modales prohibitivos: "no abras X", "sin ejecutar", "solo dime"
19|Esto es donde 4B falla más. El modelo debe demostrar que NO llama tools que abran/modifiquen X cuando se prohíbe explícitamente
20|1.4 Multi-step planning (Valor 16)
21|Detectar misiones compuestas ("abre X, busca Y, copia Z" → 3 pasos)
22|Ejecutar TODOS los pasos, no solo el primero
